## 三处系统性问题（"看不出关系"的根）

1. **一枚符号担多义**。`torii` = 今日页 + 每日条目 + 入口字段 + 空态；`koyomi` = 本月页 + 月常条目 + 版本赛季；`chochin` = 限时页 + 限时条目 + 活动组头。同一张图在表达「页面 / 周期 / 字段」三种不同的东西，用户每次都要重新猜它在指哪一层。**重设计时最该拆的就是这里**（例如周期一套、页面一套、字段一套）。
2. **同类不同图、同图不同类**。`restore` / `undo` / `refresh` 三枚都是回转箭头，只在方向上略有差别，而它们分别表示「恢复 / 撤销 / 刷新」三件事；反过来，「周常」用折扇、「月常」用历札，形状差得够开但语义全靠约定。**前者是识别度问题，后者是学习成本问题，要分开治。**
3. **功能类图标其实是通用的**。`plus` / `close` / `search` / `filter` / `grip` / `chevron-*` / `check` / `alert` 这八类不需要和风化——它们已是跨产品共识，改了只会变难认。**和风化应该只做"内容语义"那一层**（页面 / 周期 / 字段 / 奖励），通用 UI 隐喻维持现状。

## 建议的重设计分组

| 组 | 含哪些槽位 | 设计要求 |
|---|---|---|
| ① 周期 | 日 / 周 / 月 / 限时 / 一次性 / 版本赛季 | 同族、形状彼此可辨，最好有共同线索（如都带"刻度"或"圆"） |
| ② 页面 | 今日 / 本周 / 本月 / 限时 / 统计 / 工具 / 设置 | 前四个可与①共用（页面即周期）；**统计 / 工具 / 设置三枚必须有独立语义**，不能拿徽记、锤、达摩凑 |
| ③ 字段 | 入口 / 条件 / 备注 / 时间 / 收益 | 数量少、语义清晰，现有三枚（鸟居 / 锁 / 纸）已可读，可保留 |
| ④ 状态 | 成功 / 失败 / 临期 / 已完成 / 倒计时 | 「已完成」现在是铃（✗），需要一枚真正表示完成的图 |
| ⑤ 操作 | 新建 / 删除 / 编辑 / 归档 / 恢复 / 撤销 / 刷新 / 同步 / 搜索 / 筛选 / 关闭 / 排序 | **保留通用隐喻**；仅把「恢复 / 撤销 / 刷新」三枚拉开差别 |

## 改动的两种方式（工程口径）

- **只重画、不改名**：只替换 `sprite.tsx` 里对应 `<symbol>` 的 `<path>`。`IconName` 联合与约 90 处调用点**零改动**，改动面锁在 1 个文件。适合"图形不好看 / 认不出"。
- **改名（推荐配合①的拆义）**：要改 `sprite.tsx` 的 `id`、`Icon.tsx` 的 `IconName` 联合、`navIcons.NAV_ICON`、`ItemField.FIELD`、两处 `CYCLE_ICON`，以及各调用点里的字面量（30 余文件）。建议顺手改成语义名（`cycle-daily` / `nav-stats` / `nav-settings`），把"一枚担多义"在代码层面也拆开——否则下次仍会有人拿鸟居去表示第三个概念。
- 无论走哪条：**死符号要么用上、要么删**，留着会让下一个找图的人以为它在被使用 —— 按此 `sensu` 已删（2026-09-24），`shimenawa` 仍悬着（形状已修好、仍无调用点）。
